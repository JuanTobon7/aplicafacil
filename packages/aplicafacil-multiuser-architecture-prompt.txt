APLICAFACIL SERVER — MULTI-USER / MULTI-PROFILE LINKEDIN AUTOMATION REFACTOR

You are a senior backend architect and NestJS/TypeScript engineer.

I am working on `aplicafacil-server`, a NestJS backend that automates LinkedIn job discovery and job applications using Puppeteer.

I want to refactor the current LinkedIn automation architecture to properly support:

- Multiple users
- Multiple professional profiles per user
- Multiple LinkedIn accounts per user (future-proof)
- Different automation configurations per profile
- Concurrent processing of different users
- Preventing concurrent automation on the same LinkedIn account
- Redis-backed queues using BullMQ
- Stateless workers
- Reliable job/application state transitions
- Retry/failure handling
- Persistence in PostgreSQL
- Keeping Puppeteer/LinkedIn infrastructure separated from application orchestration

DO NOT implement a microservices architecture yet. Keep everything inside the existing NestJS backend. The goal is a modular monolith with queue-driven workers.

This implementation currently assumes:

- One global LinkedIn account
- One global search configuration
- One implicit user
- One implicit profile
- No queue isolation
- No execution context
- No concurrency control
- No reliable job claiming/locking

I want to remove those assumptions.

==================================================
TARGET DOMAIN MODEL
==================================================

Use the following conceptual model.

USER

One user can have multiple professional profiles.

```text
User
 ├── Profile A
 ├── Profile B
 └── Profile C
```

PROFILE

Represents the professional identity used for applications.

Examples:

- Java Backend Developer
- Full Stack Developer
- AI Engineer

A Profile belongs to exactly one User.

```text
Profile
---------
id
userId
title
summary
education
experience
skills
...
```

LINKEDIN ACCOUNT

Represents the LinkedIn account used by Puppeteer.

It belongs to a User.

```text
LinkedInAccount
----------------
id
userId
status
session/cookies information
lastLoginAt
...
```

Do NOT use environment variables for user LinkedIn credentials.

The current:

```ts
process.env.LINKEDIN_EMAIL
process.env.LINKEDIN_PASSWORD
```

approach must be removed from the multi-user automation flow.

If credentials are persisted, they must be protected appropriately.
Prefer reusable authenticated browser sessions/cookies where the existing architecture permits it.

AUTOMATION CONFIGURATION

This is the key domain concept.

An automation configuration connects:

User
Profile
LinkedInAccount
Search parameters
Application settings

Conceptually:

```text
AutomationConfig
-----------------
id
userId
profileId
linkedinAccountId

enabled

timeFilter
location
remote

maxApplicationsPerRun

createdAt
updatedAt
```

Example:

```text
User A
 ├── Profile: Java Backend
 ├── Profile: Full Stack
 │
 └── LinkedIn Account A
      │
      ├── AutomationConfig #1
      │     └── Java Backend
      │
      └── AutomationConfig #2
            └── Full Stack
```

The same LinkedIn account can eventually have multiple automation configurations, but the system MUST prevent simultaneous browser automation against the same LinkedIn account.

==================================================
QUEUE ARCHITECTURE
==================================================

Use Redis + BullMQ.

Do not perform the complete automation directly inside a @Cron() method.

The scheduler should ONLY dispatch work.

Architecture:

```text
Cron Scheduler
      │
      ▼
Find enabled AutomationConfigs
      │
      ├── Automation A → Queue
      ├── Automation B → Queue
      ├── Automation C → Queue
      └── Automation D → Queue
                    │
                    ▼
              Redis / BullMQ
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
   Search Job Worker   Application Worker
          │                   │
          ▼                   ▼
      Puppeteer           Puppeteer
          │                   │
          ▼                   ▼
       LinkedIn            LinkedIn
```

Create at least two logical queues:

```text
linkedin-search
linkedin-application
```

Use appropriate job names, for example:

```text
search-jobs
apply-job
```

The scheduler should enqueue:

```ts
{
    automationId
}
```

Do not serialize complete entities into Redis.

==================================================
SCHEDULER
==================================================

Create a dedicated scheduler responsible only for dispatching automation work.

For example:

```ts
@Injectable()
export class AutomationScheduler {

    @Cron(CronExpression.EVERY_10_MINUTES)
    async dispatchAutomations() {

        const automations =
            await this.automationService
                .findEnabledAutomations();

        for (const automation of automations) {

            await this.queue.add(
                'search-jobs',
                {
                    automationId: automation.id
                }
            );
        }
    }
}
```

Do NOT put Puppeteer operations in the scheduler.

Do NOT perform LinkedIn login in the scheduler.

Do NOT query LinkedIn from the scheduler.

==================================================
APPLICATION STATUS
==================================================

Replace the simplistic status model if necessary.

Prefer something like:

```ts
enum ApplicationStatus {
    DISCOVERED = 'DISCOVERED',
    PENDING = 'PENDING',
    PROCESSING = 'PROCESSING',
    APPLIED = 'APPLIED',
    FAILED = 'FAILED',
    CANNOT_APPLY = 'CANNOT_APPLY',
}
```

The important state transition is:

```text
PENDING
   ↓
PROCESSING
   ↓
APPLIED
```

or:

```text
PROCESSING
   ↓
FAILED
```

A worker must atomically claim an application before processing it.

Two workers must NEVER process the same application simultaneously.

==================================================
CONCURRENCY
==================================================

This is extremely important.

The system must prevent two automation jobs from using the same LinkedIn account simultaneously.

Example:

```text
LinkedInAccount A
    │
    ├── Automation A
    └── Automation B
```

Automation A and B must NOT execute Puppeteer concurrently against the same LinkedIn account.

Implement an appropriate concurrency/locking strategy using Redis/BullMQ.

The desired rule is:

ONE active LinkedIn automation execution
PER LinkedInAccount

Different LinkedIn accounts should be able to run concurrently.

Example:

```text
User A / LinkedIn A → running
User B / LinkedIn B → running
User C / LinkedIn C → running

User A / LinkedIn A → second execution MUST WAIT
```

Use BullMQ job configuration, job IDs, Redis locks, or another appropriate mechanism.

Choose the simplest robust implementation compatible with the current project.

==================================================

Keep these components separated:

```text

LinkedInLoginComponent
JobSearchComponent
```

They should NOT contain business decisions about:

RETRY STRATEGY
==================================================


- job no longer available

- user profile missing required information
